Deployment runbook

Uploading Ocellus to cPanel

A static site needs no PHP, no database and no build step on the server. You upload one folder into public_html, confirm the domain points at it, and the site is live.

Build output 75 files, 1.9 MB Server needs Apache with mod_rewrite Upload time 2 to 5 minutes

01 What you are uploading

The build produces a plain directory of files. Everything the browser needs is already in it: HTML, CSS, JavaScript, fonts and icons. Nothing is compiled on the server.

dist/cpanel/ 75 files, 1.9 MB ├── index.html the home page ├── scan/index.html the scanner, one directory per route ├── checks/index.html ├── method/index.html ├── about/index.html ├── privacy/index.html ├── terms/index.html ├── 404.html served by ErrorDocument ├── .htaccess HTTPS, headers, caching, rewrites ├── _next/static/ hashed CSS, JS, fonts and build manifests ├── *.txt route payloads Next fetches on navigation ├── favicon.ico icon.svg apple-icon.png ├── icon-16.png ... icon-512.png ├── og.png manifest.webmanifest └── robots.txt sitemap.xml

The .txt files sit beside each page and hold that route's data. They are part of the build, not leftovers, so upload them with everything else. Missing them does not break a page load, but moving between pages stops working.

Upload the contents, not the folder. The files inside dist/cpanel/ go directly into public_html. If you upload the folder itself you get public_html/cpanel/index.html and the site appears at /cpanel/ instead of the root.

02 Upload with File Manager

  1. Build the folder on your own machine

    Run npm run build:cpanel and take the dist/cpanel folder. There is nothing to install on the host.

  2. Zip it before uploading

    Compress the contents of dist/cpanel into one .zip. A single archive uploads far faster than 75 separate files, and cPanel extracts it in place.

  3. Open File Manager and go to public_html

    In cPanel, choose File Manager, then open the public_html directory. This is the document root your domain serves.

  4. Clear the default placeholder files

    New accounts often contain a default.html or a cgi-bin folder. Remove default.html so it does not shadow your index.html. Leave cgi-bin alone if it exists.

  5. Upload the archive and extract

    Use Upload, then right-click the uploaded .zip and choose Extract. Confirm the files land directly in public_html, not in a subfolder.

  6. Delete the archive

    Remove the .zip once extraction finishes so it is not publicly downloadable.

03 Upload over FTP or SFTP

Use the FTP details from cPanel under FTP Accounts. SFTP on port 22 is preferable to plain FTP when the host offers it.

Terminal, from the project root
cd dist/cpanel

# SFTP (preferred). Replace with your host, user and path.
sftp user@yourdomain.tld
  put -r * public_html/

# or with rsync, which resumes and skips unchanged files
rsync -avz --delete ./ user@yourdomain.tld:public_html/

The .htaccess file is hidden. Most FTP clients hide dotfiles by default. Turn on "show hidden files" before you upload or the server will send no security headers and every route will 404. With rsync it is included automatically.

04 Point the domain at the folder

In cPanel under Domains (or Addon Domains for a second site), confirm the domain's document root is the folder you uploaded into. For the main domain that is public_html.

If you are adding this as an extra site on a shared plan, create it as an addon domain, which gives it its own folder, and upload there instead. Do not point two domains at the same document root.

Then enable HTTPS

Under SSL/TLS Status, run AutoSSL for the domain and wait for it to issue. The site forces HTTPS in .htaccess, so a request that arrives before the certificate exists will loop. Issue the certificate first.

05 Confirm the server has what the site needs

Two Apache modules do the real work. Most shared hosts enable both, but check rather than assume.

ModuleUsed forIf it is missing
mod_rewriteHTTPS redirect and /path/ to /path/index.htmlClean URLs 404. Ask the host to enable it.
mod_headersThe eight security headers the scanner gradesPages load but grade poorly. Ask the host to enable it.
mod_deflateCompressionOptional. Pages still work, just larger.
mod_expiresCache lifetime on assetsOptional. Browsers fall back to their own defaults.

You can see which modules are loaded under cPanel's Select PHP Version or by asking the host's support. The .htaccess wraps each block in <IfModule>, so a missing module degrades quietly instead of returning a 500 error. The dotfile block carries both the Apache 2.4 and 2.2 forms for the same reason: Require all denied is a fatal error on a 2.2 server, so the file tests for the module that provides it and falls back.

A module test only proves the module is loaded. It says nothing about whether the host grants AllowOverride for a given directive. If the host allows mod_autoindex but denies AllowOverride Indexes, Options -Indexes is still a 500. That is the case the first line of the troubleshooting table below covers.

06 Verify it worked

Work down this list once the site is live. Each line is something you can check from a normal browser.

https://yourdomain.tldLoads the home page, no certificate warning
http:// yourdomainRedirects to https automatically
/scan/Loads directly, does not 404
/scanAdds the trailing slash and loads
/nonexistentShows the styled 404 page
/sitemap.xmlReturns XML, not the 404 page
/robots.txtReturns the crawl rules
FaviconShows in the browser tab

Check the headers

The site grades its own header policy, so it should send all eight. From a terminal:

Terminal
curl -sSI https://yourdomain.tld/ | grep -iE \
  'strict-transport|x-content-type|x-frame|referrer-policy|permissions-policy|cross-origin|content-security'

# Expect eight lines. Missing ones mean mod_headers is off,
# or the .htaccess did not upload (hidden files).

The strongest check: open /scan/ on your own live domain and run it. It will audit exactly the deployment you just made. All eight headers should pass, HTTPS should show a single hop, and the canonical should match the host.

500 Internal Server ErrorAn .htaccess line the server does not allowRename .htaccess to .htaccess.bak. If the site loads, the cause is confirmed. Usually a Header or Options line the host forbids.

08 Updating the site later

Rebuild, then replace the contents of public_html with the new dist/cpanel. Hashed asset filenames change with every build, so old and new files can coexist during an upload without breaking anyone mid-download. The HTML files are the only ones that must be replaced together.

Terminal, from the project root
npm run build:cpanel
rsync -avz --delete dist/cpanel/ user@yourdomain.tld:public_html/

--delete removes stale hashed assets from previous builds. Use it, but only against public_html itself and never a parent folder, because it deletes whatever is not in the source.

09 The GitHub Pages copy

The same source tree produces a second deployable for GitHub Pages, differing only in the base path. It is not an upload: the workflow in .github/workflows/deploy.yml builds and publishes it whenever you push to main.

  1. Create the repository izynu/ocellus on GitHub and push this project to it.
  2. Open Settings, then Pages, and set the source to GitHub Actions.
  3. Push to main. The workflow builds dist/pages and deploys it.
  4. The site appears at https://izynu.github.io/ocellus/.

To serve it from your own domain instead, add a CNAME record and set the repository variable SITE_URL under Settings, then Secrets and variables, then Actions. The build reads it to write absolute URLs for the sitemap, canonical tags and social preview images.

GitHub Pages cannot set response headers. The Pages copy will not send the security headers the cPanel copy does, because Pages does not read .htaccess and offers no header configuration. Its score will be lower for that reason alone. If you want one canonical, fully graded deployment, use the cPanel host and point the domain there.
